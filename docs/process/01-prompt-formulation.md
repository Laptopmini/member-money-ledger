# How the initial prompt was formulated

Nothing in this file was code; it records the analysis and the decisions the prompt
carries in, so a reviewer can tell what was decided.

## The owner's brief (summarized)

- Read the repo to work out the task and its hidden requirements. The API surely needs more
  than the two required endpoints.
- Produce a staged, checkable plan for the owner to review before any code is written. Work
  as an open debate: options, arguments, a recommendation, questions asked directly.
- Roles: owner, main session (tech lead and orchestrator), subagents (specialists), and
  Claude Design (UI, in parallel, through a handoff of at most 10 attachments and a
  handback zip unzipped into `design/`).
- Conventional commits, pre-commit/pre-push hooks, unit and E2E tests, a modern UI
  (Lighthouse), light/dark and mobile/desktop, feature flags (flagd, migratable to
  LaunchDarkly).
- Security to industry standard (rate limiting, audit log, session timeouts). As a stretch
  goal, Cloudflare's security-audit skill.
- AI only where it helps the member and is cost-effective. It must not be tied to one
  provider: any OpenAI-compatible endpoint, local or cloud.
- Developer experience, performance, and repo setup for LLM assistants (`AGENTS.md`/`CLAUDE.md`, repo skills).
- `docs/` documents the whole process. The README goes from zero to hero.
- Time box: 90 minutes from T0, on a fresh 5-hour Claude window. Minimum goals first, then
  keep going while time remains.

## Pushback the owner accepted

- **Scope versus the clock.** The brief is several hours of work. We settled on tiers
  (Must / Should / Could) that set the order, not a stopping point, plus a feature freeze at
  T+75 for docs. Parallel agents compress the work, but the git log should show the product
  arriving early, not tooling.
- **Decide before plan.** Every decision below was made in this conversation, so the build
  session's planning only covers what's genuinely open. The build session writes them up
  as ADRs.
- **`NOTES.md` is the deliverable `PROMPT.md` asks for.** Its "where AI was wrong" section
  needs a live `docs/ai-log.md`, not memory.

## Traps found during initial analysis

- the refund credit (`txn_000005`)
- pending with a null category (`txn_000004`)
- `posted_on` as a local date versus JS `Date`
- integer cents with `direction`
- transfers between the two accounts
- the offset cursor that duplicates or skips rows
- a vendor with no filters and no "changed since"
- a vendor with in-memory state
- PUT accepting any category string, with last-write-wins
- `limit=0` looping forever
- raw vendor errors

From specifically `vendor/server.py`:
- **POST validates nothing**: negative or string amounts, a bad `direction`, a bad date.
- **Path injection**: our API builds the vendor URL from user input, so ids need a strict regex.
- **`updated_at` has one-second resolution**: two edits in the same second share a timestamp.
- **A pending row that posts can change `posted_on`**, which moves it in the sort order and
  shifts the cursor mid-sync.
- **`PUT {}` bumps `updated_at`** without changing anything.
- **A negative `limit`** produces nonsense cursors.
- **Synced categories can fall outside our list**: accept them on read, validate on write.
- **The vendor has no concept of a member**, so the app is single-tenant by construction.
- **The onsite demo will be offline**: flagd, the images and the AI must not need network
  access at runtime.
- **E2E tests change the vendor's in-memory state** and need a reset between runs.

All of these move into `docs/traps.md` at T0. The build is expected to find more.
